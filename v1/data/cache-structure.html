V1 / EPHEMERAL DATA

快取與本機資料結構

現況沒有 Redis、Memcached 或共享 application cache。資料暫存分布於 client 端與單一 FastAPI process，生命週期、帳號隔離與清理邏輯各自不同。

安全界線：以下全部都可被使用者清除、修改或因換裝置而消失；只能改善體驗或減少重複呼叫。權益、角色、內容可見性與最終資料真相必須留在 Supabase / 後端。
另外，ai_usage_log.cache_*_tokens 是 Anthropic prompt cache 的計量欄位，不是 MindGym 自建的資料快取。

Process / tab 記憶體

Browser module memory

src/lib/entitlements.ts

  1. 結構：{ at: number, value: Entitlements } 或 null。
  2. Key：沒有 user id；整個 JS module 共用一份。
  3. TTL：30,000 ms；fetchEntitlements(force) 命中就不呼叫 get_my_entitlements()。
  4. 失效：invalidateEntitlements() 設為 null；重新載入自然消失。
  5. 失敗 fallback：OPEN_FALLBACK（目前功能全開的 UI 投影）。

FastAPI process resources

backend/app.py

  1. _http: httpx.AsyncClient、_claude: AsyncAnthropic：lifespan 建一次、process 關閉時釋放。
  2. 這是連線／client 重用，並非業務資料 cache。
  3. asyncio.create_task 的 AI usage 記帳是短暫 background task；失敗不重試、不持久排隊。
  4. 多 instance 時每個 process 都各自持有，沒有共用狀態。

Rate limit memory

slowapi.Limiter(key_func=_client_ip)

  1. 用途：語音辨識端點的 IP rate limit。
  2. 程式未指定 storage backend；依套件預設為單 process 記憶體型態。
  3. 重啟即清空；水平擴展時不共享計數。
  4. 這是節流狀態，不是可重用的資料快取。

localStorage：可跨重整保留的裝置本機資料

除非 key 包含 user id，這些資料皆以「瀏覽器 origin」共享，切換帳號也會看見同一份值。所有讀寫都包在 try/catch，無痕模式或配額滿時會靜默降級。

key / pattern值的資料形狀用途與生命週期帳號隔離

localStorage 的資料與隱私提醒
  • inmind-draft、gratitude-draft 可能包含使用者自由書寫內容，留在瀏覽器裝置上，不受 Supabase RLS、帳號刪除或資料庫備份政策控制。
  • Key 雖有 uid 的草稿與通知資料，但 localStorage 沒有 per-user encryption；同一瀏覽器能讀取同 origin 的帳號資料。
  • 無 user id 的 flags 會在共享裝置／切帳號時洩漏 UI 狀態；V2 應定義 account scope、schema version、TTL 與 logout cleanup policy。

sessionStorage：分頁使用階段狀態

關閉該 tab／webview session 後就消失。它不是強化的 access-control storage；尤其工作坊密碼是前端字串比對，程式本身已註明不可視為安全邊界。

key值用途／失效安全判讀
workshop_unlocked'true'四個工作坊共用的解鎖 flag；本 tab session 完結即清。不能當權限
workshop_idYYYYMMDD 或 legacy ID將工作坊貼文寫入 gratitude_entries.payload.workshop_id 的分組來源。前端可改
workshop_skip_advance_confirm'true'本次工作坊略過「不要提前翻閱」確認提示。純 UI

其他快取／暫存與外部狀態

Supabase Auth SDK storage

建立 client 時未改寫 persistence 設定；Supabase JS 預設會持久保存 session，OAuth PKCE 的 code_verifier 也會在 WebView localStorage 使用。

實際 key 由 SDK / project ref 生成，不是這個 repo 自訂的固定 key；不在上方表格計數內。

Cache Storage / service worker

hardRefresh() 會 unregister 全部 service workers，並呼叫 caches.keys() 後刪除所有 Cache API entries，再 reload。

此 repo 有清理程式，但靜態分析未發現 application 自己寫入特定 Cache Storage key；資產 cache 可能來自 PWA / 瀏覽器／部署設定。

AI provider prompt cache

Claude API response usage 的 cache_creation_input_tokens、cache_read_input_tokens 被換算成本，寫入 ai_usage_log。

實際 cache lives at Anthropic；本專案只保存計量數字，不保存／管理 prompt cache key 或內容。

V2 設計前的快取檢核

  • 為每一種 device-local data 定義：owner scope、schema version、TTL、敏感性、clear-on-logout 與可否跨裝置同步。
  • 將「草稿」明確定位為本機加密草稿或服務端 draft；不要讓本機資料在產品流程中不小心變成唯一真相來源。
  • 把 entitlement、role、rate limit、idempotency 這類跨 instance 狀態放到可信任共享層（DB / Redis / durable queue），不要依賴 tab memory。
  • 確立刷新策略：資料 API 需要 query cache / invalidation contract；靜態 assets 則需要 service worker versioning。現況的 hardRefresh() 是整體清空再 reload。
