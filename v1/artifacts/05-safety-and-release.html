安全判讀、個案紀錄與報告發布

回索引 · 基準 1e2f8cd · 2026-09-14

專業日記：保存之後才由前端要求判讀

DiaryPlayer.submit 先插入 pro_entries，再呼叫安全 API；請求失敗時才用本地關鍵字檢查與警示插入備援。 接著產生每日回饋，再視門檻要求回顧。使用者保存後關閉頁面，後續步驟可能沒有完成。

分支現況架構含義
API 關鍵字命中寫警示並回 high警示寫入 helper 未檢查 HTTP 狀態，不能等同確定保存
AI 判讀成功接受 medium／high，其他保留 none需更完整的結果 schema 驗證
AI 例外記 warning，回 HTTP 成功的 none前端 catch 不會啟動，未判讀與無風險混在一起
找不到 entry／active enrollment回 none業務拒絕與判讀結果混在一起
前端安全請求失敗或逾時本地關鍵字備援僅涵蓋客戶端仍在執行且能匹配關鍵字的情況

安全 API 雖驗證 entry 屬於本人，但分析的是 req.texts；它並未取出已保存的 answers 做對照。 這讓「這筆紀錄已被檢查」缺少可驗證的內容依據。

質性測驗：同次 AI 生成兩個視角

flowchart LR
  A[已加入個案提交答案] --> S[關鍵字 / AI 安全判讀]
  S --> R[生成 practitioner_report 與 client_report]
  R --> DB[保存 pro_assessment_results]
  DB -->|需人工或生成降級| P[pending_release]
  DB -->|不需人工| REL[released]
  P --> RPC[專業夥伴 release RPC]
  RPC --> REL
  REL --> READ[個案 RPC 僅取得 client_report]
  DB --> ALERT[有判出風險才另寫 crisis_alerts]

目前 review_before_send 或 fallback 報告中的 error 決定待發布狀態，風險值本身不是暫停發布條件。 這是應由產品／專業流程明定的決策，不在本次文件工作中擅自改變。 測驗報告保存失敗會報錯；警示在保存之後另外插入，仍有部分完成的風險。 沒有提交去重鍵，重送可能新增第二份結果並重複產生 AI 成本。

既有 SQL 的個案讀取 RPC 在 pending_release 時遮蔽 client_report，並不輸出 practitioner 版本； 這是遷移必須保留的輸出邊界，不能直接把整列結果當通用 DTO 回前端。

設計提案與驗收

拆開「處理狀態」與「判讀結果」：例如 pending／running／completed／failed，只有完成才有 risk。 以已保存答案與內容版本建立待處理工作；原始紀錄與待處理工作同交易，支援重試及人工處理失敗項目。 警示用有效唯一鍵防重並確認保存；保留後續確認、處理時間等可稽核資料。 即時 UI 求助資源與持久判讀工作各有責任，不能只依賴使用者頁面存活。

驗收包含：保存後關頁仍能完成待處理項目、AI 故障呈現未完成而非 none、修改答案使舊判讀失效、 重試不重複警示、未發布內容不洩漏、另一位 practitioner 不可發布。 此處分析的是軟體控制流程，沒有驗證判讀模型的臨床品質或替其效果背書。
