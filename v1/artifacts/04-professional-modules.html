專業模組生命週期與交易邊界

回索引 · 基準 1e2f8cd · 2026-09-14

主流程

flowchart LR
  D[專業夥伴保存草稿] --> S[Python：驗證 owner / role / status]
  S --> AI[AI 審核標籤]
  AI --> P[pending_review 與送審紀錄]
  P --> A[管理員 RPC]
  A -->|核准| PUB[draft 複製到 published_content]
  A -->|退回| REJ[rejected]
  REJ --> D
  PUB --> INV[邀請碼預覽與兌換]
  INV --> ENR[active enrollment]
  ENR --> USE[個案讀取已發布內容]

pro_modules 保存內容與狀態，pro_module_review_log 保存軌跡，invite_codes 與 pro_enrollments 分別管理加入途徑與持續關係。三種內容類型是 practice、diary、assessment。 草稿與已發布內容分開，使編輯不需要立即覆蓋個案所見內容；這個業務能力應保留。

現有交易邊界不一致

approve_module／reject_module／takedown_module 在 SQL 函式內更新狀態並寫軌跡。 Python 的 pro_submit_module 卻先 PATCH 模組、再 POST 紀錄，兩個呼叫沒有共同交易，也不檢查 status code。 HTTP 4xx／5xx 不一定讓 httpx 拋出例外，因此可能回 ok=True 但狀態或軌跡未保存。

Python 先讀草稿、等 AI、再更新；update_module_draft 只檢查 owner，未凍結送審內容。 管理員核准 RPC 又從當下的 draft_content 複製到 published，未核對先前送審版本。 因此可能出現「AI 看 A，人工核准時發布 B」；不是加個資料夾就會消失的耦合。 管理員 RPC 有角色檢查，但 UPDATE 未限制原始狀態，合法轉換規則也需重新明定。

設計提案

將這條流程封裝為 SubmitModule、ApproveModule、RejectModule、RedeemInvite 等用例。 每個用例指定 actor、允許的前置狀態與版本。送審建立不可變內容快照或 revision，AI 與人工都引用同一 revision。 狀態更新＋審核紀錄同交易，使用條件更新／版本檢查防止過期操作。 AI 不可用時記錄 failed／unavailable 的標籤狀態，仍可進人工審核，保留既有行為。

先讓 Python 調用承擔交易的 RPC 也是可行遷移步驟，不必一次將所有 SQL 業務搬走。 若日後改由 repository 直接管理交易，必須保留相同角色、狀態與資料可見性限制。

驗收

兩次送審不產生互相矛盾的軌跡；AI 等待中編輯草稿不更換送審版本；未核准草稿不對個案可見； 另一位 practitioner 不能修改他人模組；邀請碼失效與 enrollment 停止後的行為符合既有產品契約。
