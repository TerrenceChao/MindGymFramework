架構全貌、信任邊界與權益現況

回索引 · 基準 1e2f8cd · 2026-09-14

現況：一個業務有多個執行位置

flowchart LR
  UI[React / 行動 App] --> AUTH[Supabase Auth]
  UI --> API[FastAPI：AI 與部分業務編排]
  UI --> REST[PostgREST：資料表與 RPC]
  API --> AUTH
  API --> REST
  API --> AI[Claude / Whisper]
  REST --> DB[PostgreSQL：資料、RLS、函式、trigger]
  DB --> NET[pg_net]
  NET --> EDGE[Edge Functions]
  EDGE --> PUSH[APNs]
  UI --> DELETE[delete-account Edge Function]

backend/ 的 Python 檔案只有主程式、用量計算與補做腳本。主程式有 15 個 POST 與 1 個健康檢查 GET， 共用 HTTP／Claude client，route handler 同時包含驗證、查詢、prompt、業務規則與寫入。 核心資料經 Supabase REST 存取，沒有在 Python 裡直接開啟跨多個 REST 請求的資料庫交易。

路徑身分與授權主要責任
前端 → Supabaseanon key＋登入 session；RLS／RPC 驗證日記 CRUD、社群、草稿 RPC、邀請加入、讀回顧
前端 → FastAPIget_user_id 向 Auth 驗證 token；handler 檢查 ownership／enrollment／roleAI、PERMA 保存、送審、安全判讀、報告
FastAPI → Supabase共用 SUPABASE_KEY；註解與使用模式按 service key 設計需由後端自行限制使用者與資料範圍
資料庫 → Edge推播使用 webhook secret外部推播

沒有讀取環境金鑰，實際 SUPABASE_KEY 權限待部署設定確認。若為 service role，不可假設終端使用者的 RLS 會替這些請求檢查權限。

有資料表，不代表那條產品規則仍有效

Python _subscription_tier() 固定回 pro，_annotate_review_lock() 固定 locked=False。 SQL is_pro(uid) 對非 NULL uid 回 true，get_my_entitlements() 的分析上限為 -1。 但 RPC 的 tier 仍取訂閱資料列，可能是 free 且 is_pro=true；前端須以有效權益而非標籤推導功能。 因此 subscriptions、創始成員標籤與 paywall_intents 不等於已接通正式收款流程。

重構時應統一「有效權益」的決策入口，保留會員資料與量測資料的用途。不要僅憑舊註解恢復收費或額度。

優先核對的權限缺口

pro_reviews 的 UPDATE policy 名稱叫「本人可標已讀」，內容只限制 user_id，並沒有在該 policy 中限制可改欄位。 若線上有一般 UPDATE grant 且沒有額外欄位限制，使用者可能也能修改 content 等欄位。 這是靜態風險，需查實際 grants 後確認；建議改成只標已讀的 RPC／欄位權限，而非把安全性寄託在前端只送 read_at。

速讀與證據

  • 主程式 · MindGym/backend/app.py：lifespan、SUPABASE_HEADERS、get_user_id、_subscription_tier、_annotate_review_lock。
  • 前端 Supabase client · MindGym/src/lib/supabase.ts、權益讀取 · MindGym/src/lib/entitlements.ts。
  • 訂閱與有效權益 SQL · MindGym/supabase/subscriptions.sql：is_pro、get_my_entitlements。
  • 專業模組 v2 SQL · MindGym/supabase/pro_modules_v2.sql：pro_reviews policies。

驗收：使用本人、另一位使用者、專業夥伴與管理員四種身分檢查相同資源；同時覆蓋 API 與直連 Supabase。 目前沒有連線執行這些權限驗證。
