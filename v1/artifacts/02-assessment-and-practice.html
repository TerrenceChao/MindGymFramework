PERMA：回應成功與保存成功分離

sequenceDiagram
  participant U as 前端
  participant A as FastAPI
  participant L as Claude
  participant D as Supabase
  U->>A: POST /api/report：五面向敘事
  A->>D: 驗證登入 token
  A->>L: 結構化分析
  L-->>A: 分數與分析
  A->>A: 總分、體質、平衡與建議
  A->>D: INSERT perma_scores
  alt 寫入失敗
    A->>A: 記錄錯誤
  end
  A-->>U: 回傳報告（寫入失敗也可能走這裡）
  U->>D: 下次進入時讀取最近報告

report_json.scores 保留小數；p_score 等摘要欄位四捨五入後限制在 1–5。 前端優先讀完整 report_json，缺少時才用摘要分數重建。這兩種呈現精度不同，不應在遷移時只保留整數欄位。 前端請求 90 秒逾時也不等於伺服器確定沒有保存；現有 API 沒有業務請求識別碼可讓重試查回同一次結果。

日常練習：AI 與保存分成不同呼叫

業務AI 入口主要保存／附加資料
感恩/api/gratitude-summary、/api/tag-gratitude-targets前端 saveGratitudeEntry → gratitude_entries
過程目標/api/pg/focus-insight、/api/pg/focus-boost前端 → focus_logs，分享另寫 gratitude_entries
WOOP/api/woop/coach前端流程與共用社群保存，另有 increment_perma_xp RPC
專業日記/api/pro/diary-feedback先由前端寫 pro_entries，再取得 AI 回饋

gratitude_entries 還承載其他 practice_type 的日記／分享，名稱不能直接當成完整的領域定義。 saveGratitudeEntry 在插入後另行安排按讚與更新 streak；這些步驟沒有和日記插入形成同一個交易。 重構應辨識哪些是不可丟的原始紀錄，哪些只是可重算的顯示資料。

提案：定義「完成練習」的契約

  1. 保存原始作答，回傳穩定的 entry_id 與保存狀態；同一次提交帶去重鍵。
  2. AI 結果記錄輸入版本、產生狀態與模型／prompt 版本，明確區分待處理、成功、降級及失敗。
  3. streak、XP 與分享各有業務規則。必須與提交一起成立的部分進交易；可重建的統計走可重試投影。
  4. PERMA 要明確選擇「保存後才算成功」或「未保存結果仍可預覽」，API 與畫面均表達此選擇。

這些為設計建議，尚未改變現有端點或保存順序。

故障驗收

同一提交重送不新增第二筆；AI 失敗仍可找回原始作答；保存失敗不可回成已保存； streak／按讚失敗不撤銷已保存日記；歷史 PERMA 完整 JSON 與整數欄位都能重讀。
